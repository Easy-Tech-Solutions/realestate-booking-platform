# Migrating HomeKonet to a New Server

This doc covers everything that needs to move to stand the whole stack up
cleanly on a new server: the database, pgAdmin, the backend, the frontend,
and every other service in `docker-compose.yml`. See also
`docs/developer-guide.html`'s **Backup & Migration** section for the same
material in the engineering handbook, and `docs/gcp-postgres-migration.md`
for the deeper, Postgres-specific plan if the database itself is also moving
onto a new self-hosted GCP VM as part of this.

## What does NOT need migrating

| Component | Why |
|---|---|
| **Redis** | Pure cache + Celery broker + Channels layer. Empty on a fresh container is fine — it just repopulates. (Can still be backed up with `--include-redis` if you want it — see below — but it's disposable by design.) |
| **Static files** (`static_files` Docker volume) | Regenerated by `collectstatic` every time the `backend` container starts. |
| **The local LLM model** (`ai_models` Docker volume) | Re-downloadable via `manage.py download_ai_model` on the new server. Backing it up (`--include-ai-models`) only saves you the download time — worth it on a slow link, skippable otherwise. |
| **Docker images, nginx config, Dockerfiles** | All in git. `git clone` + `docker compose build` reproduces them exactly. |

## What DOES need migrating

Everything that isn't reproducible from git and isn't disposable:

| Item | Contains | Handled by |
|---|---|---|
| **The database** | Every row of real data — users, listings, bookings, payments, messages, everything. The single most important thing to get right in this whole process. | `pg_dump`/`pg_restore`, wrapped by `scripts/backup.sh`/`restore.sh` |
| **pgAdmin's saved servers** (`pgadmin_data` Docker volume) | Whoever manages the DB doesn't have to re-enter every saved connection by hand | `scripts/backup.sh`/`restore.sh` |
| `backend/media/` | Real user-uploaded photos/attachments. Irreplaceable data that lives on local disk (independent of whatever Cloudinary is or isn't configured to also hold). | `scripts/backup.sh`/`restore.sh` |
| `.env`, `backend/.env`, `frontend/.env` | Secrets: DB credentials, Stripe/Brevo/MTN keys, Django secret key, VAPID keys, pgAdmin credentials. | `scripts/backup.sh`/`restore.sh` |
| `nginx/ssl/` | The TLS cert/key. Not strictly required (you can re-issue), but copying it lets the new server serve HTTPS immediately instead of waiting on a fresh Certbot run. | `scripts/backup.sh`/`restore.sh` |
| Certbot renewal hooks | Live in `/etc/letsencrypt/` on the server, outside git. Versioned in `scripts/install-certbot-hooks.sh` so they're reproducible. | `scripts/install-certbot-hooks.sh` (re-run on the new server) |

`scripts/backup.sh` bundles the database dump, pgAdmin data, media, all
`.env` files, and the TLS cert into **one GPG-encrypted archive**.
`scripts/restore.sh` unpacks it on the new server.

> **Never `git add` a database dump, a `.env` file, or a backup archive.**
> That's exactly what this encrypted-archive mechanism exists to prevent —
> the `backups/` directory is gitignored specifically so a real backup never
> ends up in version control. See the security note at the bottom of this
> file if you're here because that already happened once.

## Migration steps

### 1. On the OLD server: take a backup

```bash
cd /opt/homekonet
bash scripts/backup.sh
```

This queries the **running `backend` container's actual environment** to find
the database connection info — it works unchanged whether the database is
external managed Postgres (Neon, via `DATABASE_URL`) or a self-hosted instance
(via discrete `POSTGRES_*` vars, see `docs/gcp-postgres-migration.md`) — then:

1. Dumps the database with `pg_dump --format=custom` (schema `public` only —
   Neon's internal `neon_auth` schema is Neon's own metadata, not our data,
   and most app-level roles can't dump it anyway).
2. Exports the `pgadmin_data` volume.
3. Archives those two artifacts plus `.env`, `backend/.env`, `frontend/.env`,
   `backend/media/`, and `nginx/ssl/` into one tarball.
4. Encrypts the tarball with GPG (symmetric — a passphrase, not a keypair).

You'll be prompted for a passphrase (or set `BACKUP_PASSPHRASE=... bash
scripts/backup.sh` to skip the prompt) — **remember it**, you'll need it to
restore. This produces `backups/homekonet-backup-<timestamp>.tar.gz.gpg`,
gitignored and encrypted since it contains live secrets and real user data.

Optional flags for the two disposable-but-transferable volumes:

```bash
bash scripts/backup.sh --include-ai-models   # + the ~3GB local LLM
bash scripts/backup.sh --include-redis       # + cache/session/broker state
bash scripts/backup.sh --full                # both of the above
```

Copy the archive to the new server:

```bash
scp backups/homekonet-backup-*.tar.gz.gpg youruser@new-server:/tmp/
```

### 2. On the NEW server: base setup

Follow `docs/DEPLOYMENT.md` §1–4 (server hardening, Docker install) if this is
a fresh box — or `docs/gcp-postgres-migration.md` §6–11 if the database is
*also* moving to a new self-hosted Postgres VM as part of this migration (in
that case, do the database VM provisioning first, so step 4 below has
somewhere real to restore into). Then:

```bash
git clone https://github.com/Easy-Tech-Solutions/realestate-booking-platform.git /opt/homekonet
cd /opt/homekonet
bash scripts/restore.sh /tmp/homekonet-backup-*.tar.gz.gpg
```

This extracts `backend/media/`, all three `.env` files, and `nginx/ssl/`
straight into the repo tree, fixes permissions (world-readable media so
nginx's worker can serve it, `600` on secrets) — and stages the database
dump and pgAdmin export in `backups/database.dump` /
`backups/pgadmin_data.tar.gz` **without restoring them automatically**.
Restoring a database is a decision only you should make explicitly (same
database as before, or a fresh one this archive should populate?), so the
script deliberately stops short and prints the exact next commands instead of
guessing.

It refuses to run if `backend/.env` already exists, to avoid clobbering a
real deployment — pass `--force` if you're intentionally re-running it.

Open `backend/.env` and update anything server-specific:
- If the database itself is moving too (not just the app server), update
  `DATABASE_URL` (or the `POSTGRES_*` vars) to point at the new database
  *before* the restore step below.
- `DJANGO_ALLOWED_HOSTS` / domain values, if anything changed.
- Consider rotating a credential while you're here, since you're touching
  this file anyway.

### 3. Restore the database

```bash
# Managed Postgres (Neon) — same project, just a new app server: skip this
# entirely, DATABASE_URL already points at the live, unchanged database.

# Fresh/different database (new Neon project, or the self-hosted VM from
# docs/gcp-postgres-migration.md) — restore into it now, before bringing
# up the stack:
pg_restore --no-owner --no-acl --clean --if-exists \
  --dbname="$(grep -m1 ^DATABASE_URL= backend/.env | cut -d= -f2-)" \
  backups/database.dump

# Self-hosted Postgres (discrete POSTGRES_* vars instead of DATABASE_URL):
source <(grep -E '^POSTGRES_' backend/.env)
PGPASSWORD="$POSTGRES_PASSWORD" pg_restore --no-owner --no-acl --clean --if-exists \
  -h "$POSTGRES_HOST" -p "${POSTGRES_PORT:-5432}" -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  backups/database.dump
```

`--clean --if-exists` drops existing objects before recreating them — safe
on a genuinely empty/fresh database, **destructive if pointed at a database
that already has different data in it**. Double-check `backend/.env` points
where you think it does before running this.

### 4. Build and do a dry run

```bash
docker compose config --quiet   # validates syntax
docker compose build
```

Don't `up` yet — DNS still points at the old server, so a real Let's Encrypt
issuance would fail domain validation from here.

### 5. Cut over DNS

Point `homekonet.com` and `www.homekonet.com` at the new server's public IP
(A record for the apex, A or CNAME for `www`). Wait for propagation — check
with:

```bash
python3 -c "import socket; print(socket.gethostbyname('homekonet.com'))"
```

until it returns the new server's IP.

### 6. TLS

If you restored `nginx/ssl/` in step 2, the site can serve HTTPS immediately
with the copied cert. Either way, once DNS has propagated to this server,
issue a fresh certificate here so renewal works going forward (the old
server no longer has DNS pointing to it, so its Certbot can't renew
anymore):

```bash
sudo apt-get install -y certbot   # if not already installed
sudo certbot certonly --standalone -d homekonet.com -d www.homekonet.com \
  --email your-email@example.com --agree-tos --non-interactive
sudo cp /etc/letsencrypt/live/homekonet.com/fullchain.pem nginx/ssl/fullchain.pem
sudo cp /etc/letsencrypt/live/homekonet.com/privkey.pem nginx/ssl/privkey.pem
sudo chown "$(id -un):$(id -gn)" nginx/ssl/*.pem
chmod 644 nginx/ssl/fullchain.pem && chmod 640 nginx/ssl/privkey.pem

bash scripts/install-certbot-hooks.sh homekonet.com
sudo certbot renew --dry-run --no-random-sleep-on-renew   # sanity check
```

(Ports 80/443 must be free — don't run this after `docker compose up` unless
you stop the `frontend` container first.)

### 7. Go live

```bash
docker compose up -d
docker compose ps                                    # everything healthy?
curl -sk https://homekonet.com/api/health/            # {"status": "ok"}
```

Smoke-test in a browser: home page loads listings with images, login works,
and (if `BREVO_API_KEY` is a real key) password reset actually sends an
email.

### 8. Restore pgAdmin's saved servers

Now that `pgadmin` has started at least once (creating the `pgadmin_data`
volume):

```bash
docker compose stop pgadmin
docker run --rm -v homekonet_pgadmin_data:/data -v "$(pwd)/backups:/backup" alpine \
  sh -c 'rm -rf /data/* && tar -xzf /backup/pgadmin_data.tar.gz -C / '
docker compose start pgadmin
```

(`homekonet_pgadmin_data` assumes the Compose project name is `homekonet` —
the default when the repo is cloned into a directory named `homekonet`;
check the actual name with `docker volume ls | grep pgadmin_data` if you
cloned it somewhere else.)

### 9. Decommission the old server

Only after you've verified the new one for a bit — keep the old server (and
its DNS-less Certbot) around as a fallback for a day or two before tearing
it down. If the database also moved off the old server's dependency (e.g.
off Neon onto self-hosted), keep the old database reachable too, read-only if
possible, until you're confident.

## Rollback

If something's wrong after DNS cutover, just point DNS back at the old
server — it's untouched and still fully functional. If the database itself
didn't move (same Neon project, just a new app server), rollback is
completely non-destructive. If the database *did* move, any writes that
happened against the new database during the verification window need to be
manually reconciled before rolling back — minimize this window by keeping it
short and by doing a dry-run restore (steps 1–3, against a scratch database)
well before the real cutover, so the final pass is fast.

## Backing up without a full server migration

`scripts/backup.sh` also works as a plain, periodic backup on the *same*
server — e.g. before a risky change, or as a nightly off-box backup via cron:

```bash
# crontab -e
0 3 * * * cd /opt/homekonet && BACKUP_PASSPHRASE="$(cat /root/.backup-passphrase)" bash scripts/backup.sh >> /var/log/homekonet-backup.log 2>&1
```

Copy the resulting archive off the server on the same schedule (e.g. `gsutil
cp` to a GCS bucket, or `rclone`) — a backup that only ever lives on the
server it's backing up isn't a real backup if that server is lost entirely.

## Security note: never commit a database dump

A database dump (or a `.env` file, or anything under `backups/`) must never
be `git add`ed, even temporarily, even on a feature branch. Git history is
effectively permanent — deleting the file in a later commit does not remove
it from history, and if the branch has been pushed, it's already on every
remote and every other clone. If a dump or secret ever *does* end up
committed, treat it as a real incident: stop, don't push further if it
hasn't been pushed yet, and escalate for a history rewrite (`git
filter-repo`) plus credential rotation rather than trying to quietly fix it
forward with a new commit.
