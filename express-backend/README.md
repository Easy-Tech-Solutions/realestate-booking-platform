# HomeKonet — standby Express backend

An independent Express/TypeScript clone of the Django backend in `../backend`.
It serves **the same API** (same paths, status codes, JSON bodies, cookies and
tokens), so the React frontend works unchanged against either one. Django is
the live backend; this is a **cold standby** you can switch to with one command.

## How it stays independent

| | Django (live) | Express (standby) |
|---|---|---|
| Compose services | `backend`, `celery`, `celery-beat`, `celery-ai` | `express-api`, `express-worker`, `express-worker-ai` (profile `express`) |
| Database | `db` | `express-db` (own volume, private network) |
| Redis | `redis` | `express-redis` (private network) |
| Media | `backend/media/` | `express-backend/media/` |
| AI model (GGUF) | `ai_models` volume, llama-cpp-python | `express_ai_models` volume, node-llama-cpp (`src/apps/aiscoring/llama_backend.ts`) |
| PDFs (leases, agreements) | WeasyPrint | headless Chromium via puppeteer-core (`src/lib/pdf.ts`) |
| Config | `backend/.env` | `express-backend/.env` (+ `.env.db`), generated by `scripts/express-init-env.sh` |

`docker compose up -d` never starts the Express services (they're under the
`express` profile). Django can't reach `express-db`/`express-redis`. Nothing in
this directory is imported by Django or vice versa.

**Same table layout:** `express-db` holds a copy of Django's schema and data
(Django's migrations remain the source of truth for the schema). That is what
makes data copies between the two plain `pg_dump`/`pg_restore` round-trips.

**Same tokens:** JWTs are signed with the same `DJANGO_SECRET_KEY` (SimpleJWT
format), and passwords use Django's PBKDF2 hash format, so users stay logged in
and keep their passwords across a switch.

## Switching

```bash
bash scripts/switch-backend.sh status
bash scripts/switch-backend.sh express   # freeze Django → copy data/media → start Express → repoint nginx
bash scripts/switch-backend.sh django    # the reverse
```

About a minute of API downtime per switch (writes are frozen while data
copies). Only the backend that's live runs background jobs
(`EXPRESS_JOBS_ENABLED`), so emails/expiry/payout jobs never run twice.
While Express is live, don't run a bare `docker compose up -d` — it would
restart Django's Celery workers.

`scripts/express-sync-data.sh to-express` refreshes the standby's data copy at
any time without switching (it refuses to overwrite whichever backend is live).

## Layout

```
src/
  server.ts, worker.ts      entry points (API / background jobs)
  app.ts                    middleware stack in Django's settings.MIDDLEWARE order
  config.ts                 env (same variable names as backend/.env)
  db/                       Kysely + generated table types (./gen-db-types.sh)
  lib/                      Django/DRF compatibility: view.ts (APIView dispatch),
                            errors.ts, jwt.ts (SimpleJWT), hashers.ts, signing.ts,
                            throttle.ts, datetime.ts, templates.ts, mail.ts, ...
  domain/                   model behaviour shared across apps (users, ...)
  apps/<django_app>/urls.ts one module per Django app, same name, same URL patterns
  routes/registry.ts        Django-style URL resolution (first match wins)
templates/                  copy of backend/templates (emails, HTML pages)
parity/                     side-by-side test suite against Django (below)
```

Routes are registered with Django's own pattern strings
(`r.path('<int:pk>/', ...)`), so coverage against Django is a direct comparison
with `parity/django-routes.json`. Every Django API route not yet ported answers
**501** `{"code": "express_not_implemented"}` rather than a misleading 404.

## Parity testing

`parity/` runs a Django instance and an Express instance, each on its own copy
of the same data snapshot (taken from `express-db`, never from production), and
replays each scenario against both, comparing status codes, JSON, cookies and
the database rows written. All outbound side effects (email, payments, MoMo,
push) are disabled in that environment.

```bash
./dev.sh npm run build && docker compose -f ../docker-compose.yml --profile express build express-api
bash parity/run.sh                      # whole suite
bash parity/run.sh tests/auth           # one file
```

## Development

Node isn't installed on the host; `./dev.sh <cmd>` runs commands in the Node 22
image (`./dev.sh npm run typecheck`, `./dev.sh npm install <pkg>`).

## Porting status

**Complete.** All Django API routes listed in `parity/django-routes.json` are
ported (none answers 501), together with the Celery tasks/beat schedules and the
Channels WebSocket consumers. The parity suite (`parity/tests/*.parity.ts`, one
file per Django app plus `core`, `auth` and `payments-providers`) passes in full.

Shared code: Django/DRF/Python compatibility lives in `src/lib/` (`view.ts`
incl. content negotiation, `fields.ts` serializer-field validation, `py.ts`
Python built-ins, `drf.ts` pagination, `upload.ts` FileField storage naming,
`jobs.ts`, `mail.ts` incl. attachments, `logger.ts`, `activity.ts`, `jwt.ts`, ...);
cross-app model behaviour lives in `src/domain/<app>.ts`. The temporary
`_deps/` copies from the porting waves are gone. See `PORTING.md` for the full
list and for the app-local helpers that intentionally stay per app.

Deliberately **not** ported:

- **Django's HTML admin** (`/admin/`, `DJANGO_ADMIN_URL`). Express answers every
  request under it with **503** and a small page saying the admin site is only
  available while the Django backend is live, pointing staff to the superadmin
  portal (`FRONTEND_ORIGIN/management`). Security headers (incl. `CSP_ADMIN`)
  are still set.

## Logs

Besides one JSON line per event on stdout (`docker logs`), Express writes the
same files, in the same line format, as Django's `logging_config.py`, under
`$LOG_DIR` (default `/app/logs`; on when `LOG_DIR` is set or
`NODE_ENV=production`, i.e. in the image): `application.log` (one line per
request + activity/transaction events), `activity.log`, `transactions.log`,
`errors.log` (WARNING+ incl. `django.request` 4xx/5xx lines), each rotating at
10 MB × 10. So platform-ops' log viewer, recent-errors and system-health show
Express's own logs while Express is live. `express-api` and `express-worker`
should share one named volume (`express_logs`) at `/app/logs`; if the directory
isn't writable, file logging switches itself off with one note on stderr.
